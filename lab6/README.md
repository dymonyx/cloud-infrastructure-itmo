# Лабораторная работа 6

## Что находится в работе

Для Chainwise я выбрала PostgreSQL, потому что проект уже работает с реляционными данными о велосипедах, велопоездках и обслуживании. В стенде есть основной узел и одна standby реплика со streaming replication.

Тестовой сущностью стала велопоездка. Она хранится в таблице `trips` и содержит идентификатор велосипеда, расстояние, маршрут и время создания. `bike-api` записывает данные в primary, а список получает со standby. Адреса обеих баз передаются через `WRITE_DB_HOST` и `READ_DB_HOST`.

Вместе с базами запускаются `postgres_exporter`, Prometheus и Grafana. Вся конфигурация находится в `docker-compose.yml`, а для переключения после failover используется `docker-compose.failover.yml`.

## Запуск

Команды выполняются из папки `lab6`.

```bash
cp .env.example .env
docker compose up -d --build --wait
docker compose ps
```

Страница `bike-api` доступна по адресу [http://localhost:8081](http://localhost:8081), Prometheus открывается на [http://localhost:9090](http://localhost:9090), а Grafana на [http://localhost:3000](http://localhost:3000).

Состояние репликации можно проверить отдельным скриптом.

```bash
./scripts/verify-read-write-split.sh
```

Primary должен показать `is_standby = f`, а реплика `is_standby = t` и `read_only = on`. В `pg_stat_replication` соединение `chainwise-standby` должно иметь состояние `streaming`.

## Репликация и lag

Primary запускается с `wal_level=replica` и использует физический слот `chainwise_standby_slot`. При первом запуске standby делает базовую копию через `pg_basebackup`, создаёт `standby.signal` и после этого начинает получать WAL.

Обычная локальная репликация работает слишком быстро, поэтому для проверки lag применение WAL временно останавливается.

```bash
./scripts/pause-replica.sh
```

После этого через кнопку `Налить нагрузку` в primary добавляется пачка записей. Во время проверки primary уже видел `1001` запись, а standby только `1`. Разница WAL составила около `336 KiB`, при этом полученная и применённая позиции LSN отличались.

Размер отставания можно измерить на primary с помощью `pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)`, где `replay_lsn` берётся из `pg_stat_replication`. Функция возвращает количество байтов WAL, которые standby ещё не применила. Время задержки можно смотреть в поле `replay_lag`, а на самой standby дополнительно сравнивать `pg_last_wal_receive_lsn()` и `pg_last_wal_replay_lsn()`.

Текущее состояние можно посмотреть так.

```bash
./scripts/show-replication.sh
```

После проверки применение WAL нужно продолжить.

```bash
./scripts/resume-replica.sh
```

Через несколько секунд standby догоняет primary, количества записей сравниваются, а lag возвращается к нулю. Для Chainwise временно устаревшее чтение опасно тем, что только что добавленная велопоездка может не появиться в списке, а расчёт пробега некоторое время будет использовать старые данные.

## CAP

Асинхронная репликация больше смещает этот стенд в сторону доступности чтения. Standby может продолжать отдавать уже применённые данные, даже если primary или связь с ним недоступны, но последние изменения в этот момент могут отсутствовать. При сетевом разделении узлы смогут отвечать на запросы, хотя данные на них уже не будут совпадать, поэтому доступность сохраняется за счёт согласованности.

Для смещения в сторону согласованности на primary нужно указать синхронную реплику через `synchronous_standby_names`, например `FIRST 1 ("chainwise-standby")`. Если подтверждённая запись должна быть уже применена на standby, можно установить `synchronous_commit=remote_apply`, а критичные чтения отправлять на primary. Тогда каждый commit будет ждать реплику, поэтому увеличится задержка и снизится скорость записи. При недоступной standby или связи с ней новые транзакции будут ждать подтверждение, то есть за согласованность придётся заплатить частью доступности.

## Failover

Перед failover оба подключения работали в обычном режиме. Новые велопоездки записывались в primary, а список читался со standby. Сначала standby догнала primary, после чего основной контейнер был остановлен.

```bash
docker compose stop postgres-primary
```

После остановки primary запись перестала работать, потому что write подключение всё ещё указывало на остановленный узел. Чтение при этом продолжило работать и standby отдавала все уже применённые данные.

Затем standby была повышена до primary вручную. Сразу после промоушена чтение продолжало работать уже с повышенного узла, но запись всё ещё завершалась бы ошибкой, пока write подключение оставалось направлено на старый primary. Поэтому после промоушена сервис был переключён через второй compose файл.

```bash
./scripts/promote-standby.sh
./scripts/switch-service-to-promoted.sh
```

Состояние контейнеров и роль повышенного узла можно проверить отдельными командами.

```bash
docker compose ps -a postgres-primary postgres-standby bike-api

docker compose exec -T postgres-standby sh -c '
  psql --username "$POSTGRES_ADMIN_USER" --dbname "$POSTGRES_DB" --no-psqlrc --command "
    SELECT pg_is_in_recovery() AS is_standby,
           count(*) AS trips
    FROM trips;
    SHOW transaction_read_only;
  "
'
```

Старый primary должен быть остановлен, а у повышенного узла `is_standby` должен быть равен `f` и `transaction_read_only` должен быть равен `off`.

После переключения обе переменные подключения стали указывать на повышенный узел. Запись снова заработала, а список сразу прочитал новую велопоездку из той же базы. Неудачный запрос, сделанный во время отказа, сам не повторился, поэтому после восстановления была создана новая запись.

Старый primary нельзя просто запускать обратно. За время его отсутствия на новом primary появляются другие данные, поэтому одновременная работа двух узлов приведёт к split brain. Старый узел нужно изолировать и заново создать от нового primary. В рабочем окружении такой процесс можно автоматизировать через Patroni и etcd или Consul, а старый лидер блокируется через fencing.

## Мониторинг

На дашборде Grafana видны доступность write и read базы, количество записей, отставание WAL, подключения к PostgreSQL, транзакции и ошибки записи.

Для алертов выбраны три метрики.

1. `chainwise_postgres_write_database_up` показывает, может ли сервис сохранять новые велопоездки. Алерт срабатывает, если write база недоступна 10 секунд, потому что в таком состоянии новые записи завершаются ошибкой.

2. `chainwise_postgres_replica_lag_bytes` показывает разницу WAL между primary и standby. Порог равен `16 KiB` в течение 15 секунд, потому что растущее отставание приводит к устаревшему чтению и увеличивает объём последних данных, которых не будет на реплике при аварии.

3. `pg_stat_database_numbackends` показывает число подключений к базе `chainwise` на каждом узле. Для лабораторного стенда задан порог 20 подключений в течение минуты, чтобы заранее увидеть приближение к лимиту, после которого новые запросы не смогут подключиться к PostgreSQL.

Правила находятся в `monitoring/prometheus/alerts.yml`, а готовый дашборд в `monitoring/grafana/dashboards/chainwise-postgres.json`.

## Остановка

Обычный стенд можно остановить без удаления данных.

```bash
docker compose stop
```

После failover используются оба compose файла.

```bash
docker compose -f docker-compose.yml -f docker-compose.failover.yml down
```

Для полностью чистого запуска удаляются тома этой лабораторной.

```bash
docker compose -f docker-compose.yml -f docker-compose.failover.yml down -v
docker compose up -d --build --wait
```
